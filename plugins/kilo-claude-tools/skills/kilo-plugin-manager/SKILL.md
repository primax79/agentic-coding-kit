# Kilo plugin manager

Emulates Claude Code's plugin-marketplace mechanism for Kilo Code (and keeps
Claude Code in sync on the same machine). A marketplace is a git repo in Claude
Code's plugin layout (`.claude-plugin/marketplace.json` + plugins with
`skills/`, `agents/`, `commands/`), so one repo serves Claude Code users
natively and everyone else through this skill.

**Everything is done by the bundled script — never perform these steps by
hand (no manual git clone, symlinking, or frontmatter editing).**

Depending on how `kilo-plugin-manager` was installed on your machine, run the script from either location:

- **If installed via `skills.urls` (Local Config / Cached)**:

  ```bash
  python3 ~/.cache/kilo/skills/kilo-plugin-manager/scripts/plugin_manager.py <subcommand>
  ```

- **If installed globally via Marketplace / Symlink**:

  ```bash
  python3 ~/.kilo/skills/kilo-plugin-manager/scripts/plugin_manager.py <subcommand>
  ```

| Task                                        | Command                                           |
| ------------------------------------------- | ------------------------------------------------- |
| Register/refresh a marketplace              | `add <git-url-or-path> [--name N]`                |
| See available plugins + installed state     | `list`                                            |
| Install a plugin globally                   | `install <plugin>[@marketplace]`                  |
| Install into one repo only                  | `install <plugin> --project <repo-path>`          |
| Update everything (pull + refresh installs) | `update`                                          |
| Remove a plugin's files                     | `uninstall <plugin> [--project <repo-path>]`      |
| Show marketplaces, HEAD commits, installs   | `status`                                          |
| Convert one agent file Claude↔Kilo         | `convert <file.md> --to kilo\|claude [-o out.md]` |
| Scaffold a new marketplace repo             | `init-marketplace <path> [--name N]`              |

## How installs work (for explaining to the user, not for re-implementing)

- **Skills** are symlinked from the marketplace checkout (`~/.kilo/marketplaces/<name>/`)
  into `~/.kilo/skills/` or `<repo>/.kilo/skills/`, so `update` propagates
  instantly. `--copy` copies instead (use for project installs that must not
  depend on the local checkout; note project-installed symlinks are
  machine-specific — gitignore them or use `--copy`).
- **Agents** are generated: Claude-shaped sources (`tools:` frontmatter) are
  translated to Kilo shape (`mode`/`permission`) into `.kilo/agent/`, and
  vice versa into `.claude/agents/` (skip with `--no-claude`). Generated files
  carry a "generated by kilo-plugin-manager" marker — edits belong in the
  plugin source repo.
- **State** lives in `~/.kilo/plugin-manager.json`. The script only ever
  overwrites or deletes paths it recorded there; pre-existing user files are
  warned about and left alone.
- `.claude/skills` is symlinked to `.kilo/skills` when missing (same
  convention as the kilo-claude-sync skill).

## Typical team workflow (d4science/gCube)

1. Maintainer: `init-marketplace ~/works/gcube/ai-toolkit --name gcube`, move
   real skills/agents into `plugins/<plugin>/`, bump `version` in
   `plugin.json`, commit, push to Gitea.
2. Claude Code users: `claude plugin marketplace add <gitea-url>` +
   `/plugin install <plugin>@gcube` (native, no script needed).
3. Kilo/other users: `add <gitea-url> --name gcube` + `install <plugin>@gcube`.
4. Everyone updates with `update` (or Claude's native plugin update).

If the user asks for something the script has no subcommand for, prefer
extending the script over doing it manually in the conversation.

## Bootstrapping & Skill-only Project Configuration (via URL index)

To initially bootstrap `kilo-plugin-manager` on a new machine, or to quickly provision a project with a set of skills without cloning the marketplace repository, Kilo's native remote skill-loading mechanism can be used.

### 1. The `skills.urls` Mechanism

Kilo can pull skills directly from a remote HTTP index. By pointing `skills.urls` in `kilo.jsonc` to the parent folder containing `index.json` (and **not** to individual files or the specific subfolder directly), Kilo will:

- Fetch the remote `index.json` manifest.
- Download and namespace each listed skill into its own cache subfolder under `~/.cache/kilo/skills/<plugin-name>/`.

For example, to bootstrap the tools of the `gcube-ai-toolkit` suite:

```jsonc
{
  "skills": {
    "urls": [
      "https://code-repo.d4science.org/gCubeSystem/gcube-ai-toolkit/raw/branch/main/plugins/common-tools/skills/",
      "https://code-repo.d4science.org/gCubeSystem/gcube-ai-toolkit/raw/branch/main/plugins/gcube-core/skills/",
      "https://code-repo.d4science.org/gCubeSystem/gcube-ai-toolkit/raw/branch/main/plugins/kilo-tools/skills/",
      "https://code-repo.d4science.org/gCubeSystem/gcube-ai-toolkit/raw/branch/main/third-party/skills/"
    ]
  }
}
```

*Note on Paths:* When loaded via `urls`, the script location is cached under `~/.cache/kilo/skills/kilo-plugin-manager/scripts/plugin_manager.py` instead of the global `~/.kilo/...` directory.

### 2. Why the Plugin Manager is Still Necessary (The Agent Limitation)

While the `urls` mechanism is extremely efficient for provisioning **skills**, **Kilo does not support loading Agents via remote URLs**.
Agents (`.md` files defining custom system prompts, permissions, and steps) can only be loaded from local filesystem directories (such as `.kilo/agent/` or `~/.kilo/agent/`).

Therefore, we must continue to use `kilo-plugin-manager` to:

- Globally or project-locally install **Agents** from the marketplace.
- Bidirectionally synchronize and translate agent definitions between Claude Code (`.claude/agents/`) and Kilo Code (`.kilo/agent/`).
- Copy or symlink assets that require local integration or persistent synchronization.
